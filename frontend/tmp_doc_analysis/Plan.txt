Resumen
         Este plan establece cómo se organizará, desarrollará, integrará y controlará GestNutri,

una aplicación web para la gestión y seguimiento de pacientes de nutrición. El equipo estará
formado por cuatro integrantes que trabajarán desde computadoras diferentes sobre un único
repositorio de GitHub. El proyecto utilizará Scrum para organizar el trabajo en Sprints y tendrá
como fecha límite el 10 de octubre de 2026. La solución se desarrollará con React, Django,
Django REST Framework y PostgreSQL.

         La inteligencia artificial se utilizará en dos niveles claramente diferenciados. Primero,
cada integrante podrá utilizar IA en su propia computadora como apoyo para analizar, programar,
probar, documentar y revisar su tarea. Segundo, existirá un Agente Orquestador con contexto
global del proyecto, encargado de relacionar el trabajo publicado por los integrantes, detectar
dependencias e inconsistencias y sugerir acciones de integración. El Agente Orquestador no
sustituye GitHub, Scrum ni la revisión humana.

1. Descripción, objetivos y alcance

GestNutri es una aplicación web orientada a profesionales de nutrición. Su propósito es

centralizar la información de los pacientes y facilitar el seguimiento entre consultas. El proyecto

responde a la necesidad de reducir la dispersión de información en notas, archivos y

herramientas independientes, y de disponer de una visión clara de la evolución de cada paciente.

El objetivo general es desarrollar, integrar y validar antes del 10 de octubre de 2026 un

producto mínimo viable (MVP) que permita administrar pacientes, registrar consultas y

mediciones, consultar historial, comparar automáticamente la evolución y utilizar inteligencia

artificial de forma controlada para apoyar la redacción de notas.

El Product Goal es disponer, al cierre del proyecto, de una versión demostrable de

GestNutri que permita al nutricionista completar el flujo básico de seguimiento de un paciente

desde su registro hasta la revisión de su evolución, manteniendo trazabilidad del desarrollo,

seguridad básica y revisión humana de las funciones asistidas por IA.

4. Forma de trabajo con Scrum

Cada Sprint tendrá un Sprint Goal y deberá producir un Increment integrado y

demostrable. En Sprint Planning se seleccionarán las historias prioritarias y se identificarán

dependencias; la Daily Scrum, de hasta 15 minutos en los días de trabajo, permitirá inspeccionar

el avance y ajustar el plan; la Sprint Review demostrará el resultado; y la Sprint Retrospective

identificará mejoras para el siguiente ciclo.

Artefacto / compromiso                         Uso en GestNutri
Product Backlog / Product Goal                 Concentra las historias del producto y
                                               mantiene visible el objetivo general del MVP.
Sprint Backlog / Sprint Goal                   Contiene las historias y tareas seleccionadas
                                               para cumplir el objetivo del Sprint.
Increment / Definition of Done                 Resultado integrado que cumple criterios de
                                               aceptación, pruebas, revisión y condiciones de
                                               calidad.

         Una historia estará preparada para un Sprint cuando sea comprensible, tenga criterios de
aceptación, dependencias identificadas y datos de prueba. Estará terminada cuando cumpla los

7. Arquitectura y tecnologías

GestNutri utilizará una arquitectura cliente-servidor. React implementará la interfaz;

Django y Django REST Framework expondrán la API y concentrarán autenticación,

autorización, validaciones y lógica de negocio; PostgreSQL almacenará la información. Las

funciones de IA del producto se invocarán desde el backend para evitar exponer credenciales en

el navegador.

8. Desarrollo distribuido con Git y GitHub

Cada integrante tendrá un clon local del mismo repositorio. main contendrá la versión

estable; develop será la rama de integración; y las historias se desarrollarán en ramas

feature/HU-XX-descripcion. También podrán utilizarse fix y docs.

Paso                                             Procedimiento
1. Sincronizar                                   Actualizar develop y revisar cambios
                                                 recientes.
2. Crear rama                                    Crear o actualizar la rama de la historia.
3. Desarrollar                                   Programar y probar localmente, con IA de
                                                 apoyo cuando resulte útil.
4. Publicar                                      Commit descriptivo y push a GitHub.
5. Revisar                                       Pull Request a develop, CI, revisión humana y
                                                 observaciones del Orquestador.
6. Integrar                                      Corregir, aprobar y fusionar; el resto del
                                                 equipo vuelve a sincronizar.

         GitHub será la fuente oficial del código y del estado compartido. El equipo no integrará
el sistema enviando carpetas completas entre computadoras. Los commits utilizarán prefijos
como feat, fix, test, docs, refactor y chore.

10. Agente Orquestador con contexto global

El Agente Orquestador es distinto de la IA local de cada desarrollador. Su propósito es

mantener una visión integral de GestNutri y ayudar a coordinar el trabajo que se publica desde

las cuatro computadoras. GitHub conserva el código y el historial; el orquestador interpreta ese

estado, relaciona cambios y formula recomendaciones.

         El orquestador complementará a Git detectando conflictos semánticos. Por ejemplo, si
React espera phoneNumber y Django devuelve phone, Git puede fusionar ambos cambios sin
conflicto textual, pero la aplicación fallará. El orquestador deberá advertir la incompatibilidad.
También podrá detectar migraciones faltantes, pruebas no actualizadas, duplicación de trabajo o
documentación obsoleta.

         El agente puede sugerir ideas porque conoce el proyecto completo, pero no puede
convertirlas por sí mismo en requisitos. Las propuestas de alcance deben pasar por el Product
Owner; las decisiones de proceso corresponden al Scrum Team; y las decisiones técnicas
importantes requieren revisión humana. El orquestador no aprobará su propio trabajo, no
fusionará directamente a main, no eliminará cambios ajenos y no sustituirá al Scrum Master.

11. Gestión de requisitos y cambios

Los requisitos se administrarán como historias en el Product Backlog. Una solicitud

nueva se registrará, se analizará por valor, esfuerzo, dependencias, riesgo e impacto sobre la

fecha y será ordenada por el Product Owner. Los cambios que afecten arquitectura, contratos de

API, datos o seguridad deberán documentarse antes de integrarse.

manejarán con los mecanismos seguros del framework y variables de entorno; no se almacenarán

claves en Git. En desarrollo se utilizarán datos ficticios o anonimizados. La IA del producto

deberá ser degradable: si el servicio no está disponible, las notas manuales seguirán funcionando.

15. Entregables y criterios de aceptación
         Los entregables serán: repositorio GitHub con historial; frontend React; backend

Django/DRF; modelo y migraciones PostgreSQL; Product Backlog y evidencia de Sprints;
pruebas y CI; documentación de API; reglas y descripción del Agente Orquestador; guía de
instalación; manual breve; plan de gestión; MVP demostrable y presentación final.

         El MVP será aceptado cuando un usuario autorizado pueda iniciar sesión, administrar
pacientes, registrar consultas y mediciones, consultar historial, visualizar correctamente la
evolución, guardar notas sin depender de IA y utilizar opcionalmente la formalización con
revisión humana. También deberá demostrarse que React consume la API Django, los datos
persisten correctamente y el trabajo distribuido fue integrado mediante GitHub, Pull Requests, CI
y revisión.

16. Conclusiones
         El plan organiza GestNutri alrededor de una fecha fija, un único producto y un equipo

distribuido. Scrum proporciona objetivos, inspección y adaptación; Git y GitHub permiten
integrar el trabajo de cuatro computadoras; la IA local apoya a cada desarrollador; y el Agente
Orquestador aporta contexto global para detectar dependencias e inconsistencias desde el primer
Sprint. La combinación de Product Goal, backlog trazable, pruebas, CI, gestión de riesgos y
revisión humana permite mantener el proyecto controlado sin convertir el plan en documentación
innecesariamente extensa.
